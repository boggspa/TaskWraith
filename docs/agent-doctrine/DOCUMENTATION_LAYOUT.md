# Documentation layout doctrine

Read this file in full before adding, moving, renaming, or deciding the publication status of any markdown document.

## Why this file exists

`.gitignore:35` ignores `docs/` wholesale, and 147 of the 171 `docs/**/*.md`
files present in this checkout are force-added past that line individually.
Until this document existed there was no written rule deciding which 147.
Publication status was set by whoever last ran `git add -f`, and the two failure
directions are not symmetric: an unpublished doc that source cites dangles on
every fresh clone, and a published doc that should have stayed private cannot be
recalled from a public repository. Both have already happened here.

## Where a doc belongs

- **Repository root is reserved for fixed-name discovery.** `README.md`,
  `CHANGELOG.md`, `SECURITY.md`, `AGENTS.md`, and `CLAUDE.md` live at the root
  because a tool, a host, or a code-hosting UI looks for that exact filename in
  that exact place. Nothing else earns a root file. This is enforced, not
  advisory: `scripts/agent-doctrine-reach.test.ts` pins `CLAUDE.md` to the root
  because Claude-family sessions discover only that path, and
  `178f175fe` ("restore CLAUDE.md to repo root after docs relocation broke the
  Claude delivery route") is the commit that put it back after a tidy-up moved
  it. `docs/CLAUDE.md` is now a tombstone saying so.
- **`docs/` is reader-facing material** — anything a human opens to understand
  the product, a subsystem, or a decision.
- **A co-located `*.md` is legitimate only where the doc is structurally bound
  to its sibling code.** Two real cases: `resources/Tools.md` is generated by
  `src/main/ollama/OllamaToolsDoc.ts` from `src/main/McpToolCatalog.ts` and
  drift-tested against it, so it is an output of that directory, not prose about
  it; `src/tui/DESIGN.md` is the design contract its sibling `src/tui/theme.ts`
  implements, and it deliberately refuses to restate cut-point numbers because
  restating them is how documentation drifts. If your doc would survive
  unchanged when the sibling code is deleted, it is not bound to it — it belongs
  in `docs/`.
- **`.local-only/` is the private twin.** It is gitignored at the top of
  `.gitignore` with no force-add convention, so a file placed there is private by
  construction rather than by anyone remembering.
- **A family of related docs gets a subdirectory, not a flat name prefix.**
  `docs/agent-doctrine/`, `docs/how-to/`, `docs/security/`, `docs/refactors/`,
  and `docs/performance/` are the pattern. A prefix family such as the nine
  flat `channels-*.md` files reads as nine unrelated documents in a listing and
  cannot be published, ignored, or moved as a unit.

## The publication test

**If tracked source cites a doc by path, that doc must be tracked.**

This is the load-bearing rule in this file. A `docs/…` path in a source comment
is a promise to whoever clones the repository. When the doc is not tracked, the
promise breaks on the first fresh clone, and it breaks silently — no compiler,
no test, and no linter reads a path out of a comment. Five references in tracked
source name docs that are not in `git ls-files` today:

- `src/main/ProviderQuotaWallClassifier.ts:11` →
  `docs/auto-failover-killswitch-spec.md`
- `src/main/services/EnsembleBackgroundDispatch.ts:67` →
  `docs/bg-user-mention-posture-design.md`
- `relay/src/server.ts:76` and seven more source files →
  `docs/ios-push-gateway-design.md`
- `src/main/HostToolResolver.ts` and `src/main/documents/PdfTextExtractor.ts` →
  `docs/audio-video-pipeline-design.md`
- twelve source files, including `src/main/index.ts`,
  `src/main/EnsemblePrompt.ts`, and `src/main/services/EnsembleOrchestrator.ts` →
  `docs/ensemble-posture-fanout-preamble-design.md`

Two ways to satisfy the test, and you must pick one deliberately:

1. Force-add the doc (`git add -f docs/<name>.md`) so the citation resolves.
2. Remove the citation, or reduce it to a description that does not promise a
   file — then mark the doc as deliberately unpublished, below.

Leaving it unresolved is not a third option. Check your own additions with
`git ls-files -- <path>` before you commit a comment that names one.

## Marking deliberate non-publication

A doc that must stay private needs an **explicit inline banner saying so**,
because that banner is the only thing separating "deliberately private" from
"someone forgot to force-add it". Without it the two are indistinguishable, and
the next agent tidying up the tree has to guess.

Two files already do this correctly and are the templates:

- `docs/competitive-popularity-analysis.md` opens with an HTML comment naming
  the gitignore line, stating the file is not in `git ls-files`, and instructing
  that it must **never** be force-added.
- `docs/privacy-data-flow-statement.md` records the opposite state: publication
  approved on a named date by a named person, with the exact preconditions that
  must land first, and an explicit note that publishing is a deliberate
  `git add -f` on that file only.

Note that the second one also names its sibling and forbids force-adding it.
That is the shape to copy: say what the state is, who decided, and what would
change it.

## A move commit changes publication status

`git mv` is not a neutral operation in a tree where publication is decided by
force-add against a wholesale ignore.

The incident: `758b47e14` ("chore: keep security ledger local-only") deliberately
made the Security Engineering Ledger private by adding a **root-anchored**
`/SECURITY_ENGINEERING_LEDGER.md` rule and deleting 2,139 tracked lines.
Thirteen days later `298f9c2b0` ("chore(docs): move internal paperwork to docs
directory") moved that file to `docs/SECURITY_ENGINEERING_LEDGER.md` — a path
the anchored rule cannot match — and it re-entered the tracked tree as 2,176
added lines. Fifteen of that commit's sixteen entries were pure renames showing
`0` changed lines, so the one entry that was actually a publication did not look
like one in review.

Two rules follow:

- **Anchor ignore rules so they survive a move**, or accept that they only
  protect one path. `/X.md` protects the root and nothing else; a bare `X.md`
  pattern matches at any depth.
- **Re-check tracking status after any doc move**, in both directions:
  `git ls-files -- <newpath>` for accidental publication, and
  `git log --diff-filter=D --oneline -- <oldpath>` plus a check that the citation
  sites still resolve for accidental un-publication.

`TW_ALLOW_IGNORED_ADD=1` exists precisely because a `git mv` of an
already-tracked doc trips the commit hook's gitignored-add block — see
[Committing](REPOSITORY_WORKFLOW.md#committing). Treat that prompt as the
question it is, not as noise to override.

## Relative links break on move

`298f9c2b0` was a pure rename with **zero** content edits, and that is exactly
why it broke links: nothing in the diff showed a link, so nothing in review
showed the breakage. Measured against that commit:

- **10 `README.md` links** pointed at root-relative filenames
  (`POSITIONING.md`, `SAFETY.md`, `TRUST_AND_SAFETY.md` three times, and five
  others) that were no longer at the root.
- **10 provider-logo image paths** in `MODEL_CATALOGUE.md` resolved from the
  root (`design-assets/provider-logos/png/provider-logo-*.png`) and now resolved
  from inside `docs/`.
- **4 inbound `how-to` links** — in `docs/how-to/composer/README.md`,
  `docs/how-to/composer/provider-model-permissions-pickers.md`,
  `docs/how-to/settings-and-configuration/README.md`, and
  `docs/how-to/settings-and-configuration/general-tab.md` — climbed with `../`
  to files that had moved down into `docs/`.

So: before moving a doc, grep for inbound links to its old path and for
outbound relative links inside it, and fix both in the same commit. A rename
with a zero-line diff is the most dangerous shape a doc change can take.
